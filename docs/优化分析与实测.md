# 项目优化分析与实测记录

## 这次解决了什么

问答工作流原先依次执行“意图识别 → 查询改写”。这两个步骤都只依赖用户问题，串行等待会让第二次模型请求白白排在第一次后面。现在两步在 LangGraph 的同一轮并行开始，检索节点等待两者都完成后再执行。直接调用 `QAAgent.answer()` 的路径也同步改成并发。

第二个问题出在检索评测：网页上传时服务把原始文件名改成受管随机 ID，原有 golden set 却按原始文件名判断来源。文档内容检索正确也可能被计为未命中。现在评测可用 `--api-url` 读取文档目录，将受管 ID 映射回原始文件名；缺失或同名多份会报错，避免产生误导性分数。

第三个改进是阅读流程：API 和页面将受管 ID 显示为原始文件名，并按答案中的 `[1]`、`[2]` 编号列出证据。回答与来源能一一对应。

| 改动 | 原流程 | 现流程 | 可核对结果 |
|---|---|---|---|
| 问答预处理 | 意图识别结束后才开始改写 | 两个独立步骤同时执行，汇合后检索 | 下方受控延迟实验；调用次数不变 |
| 来源评测 | 受管 ID 与 golden set 原名不匹配，可能出现假零分 | 通过文档目录还原文件名，缺失或歧义时报错 | 自动化测试覆盖映射和错误场景 |
| 用户查看证据 | 只显示受管文件路径 | 显示原始文件名和证据编号 | API 测试覆盖来源转换 |

## 已运行的量化实验

这是一项**本地模拟 I/O 的工作流耗时实验**。同一套 LangGraph 节点、同一批 30 个问题，先热身，再重复 3 轮；两种流程轮流先运行，使用 `time.perf_counter()` 记录 90 次请求各自的耗时。假 Agent 用 `asyncio.sleep` 模拟各阶段等待：意图 40 ms、改写 60 ms、检索 15 ms、Self-RAG 8 ms、生成 25 ms。

| 端到端工作流 | P50 | P95 | 平均值 |
|---|---:|---:|---:|
| 串行预处理 | 185.728 ms | 187.383 ms | 182.293 ms |
| 并行预处理 | 123.984 ms | 138.879 ms | 122.693 ms |
| 差值 | **节约 61.744 ms，P50 降低 33.24%** | 节约 48.504 ms | 节约 59.600 ms |

两种流程的 `classify/rewrite/retrieve/self_rag/generate` 调用数完全相同：每步都是 92 次（90 次测量 + 2 次热身）。90 次输出逐一比较一致。并发减少等待时间，并没有减少模型调用次数或 token 用量。

现有增量更新回归测试还提供了另一项**处理量**证据：3 个 chunk 的文档只修改 1 个 chunk 时，重新向量化与重新抽取均只处理 1 个，另外 2 个复用；相对于对这 3 个 chunk 全量重做，该场景减少 2/3 的重处理量。内容完全未变的测试中，重处理量为 0。这是测试里的任务量计数，尚未换算成真实耗时或模型费用。

原始数据：[qa_preprocessing_latency.json](./evidence/qa_preprocessing_latency.json)。数据集 SHA-256、运行环境、每阶段假定延迟、热身数、重复次数、输出一致性和调用次数都在 JSON 中。

从项目根目录复现：

```bash
cd python
python benchmarks/qa_preprocessing_latency.py \
  --dataset benchmarks/golden_set.jsonl \
  --samples 30 --runs 3 \
  --out ../docs/evidence/qa_preprocessing_latency.json
```

**适用边界：** 上述数值只说明在给定模拟等待时间下，当前工作流能减少关键路径上的串行等待。它没有调用真实 LLM 或数据库，没有测量实际业务延迟、答案准确率、人工节省时间或线上成本。真实模型服务可能有并发限制、排队和限流；要把性能数字写成生产效果，必须固定模型、硬件、语料和并发量，在实际部署中重复压测。

## 现状与下一步

当前项目已经覆盖文档入库、向量与图谱检索、来源追踪、人工审核、增量更新、流式问答和自动化测试。它是 **Agent 应用与评测工程**；尚未采集可训练的状态—动作—观察轨迹，也没有 SFT、DPO 或 RL 的训练前后对照实验，因此不能称为 Agent 后训练项目。

下一步最值得投入的三件事：

1. 用独立人工标注集评测真实检索与答案，记录 Recall、答案正确性、引用正确性和拒答率。仓库现有 30 题示例集只适合演示评测流程。
2. 在真实 LLM + Qdrant + Neo4j 环境测量节点级延迟、请求成本和并发能力，校验本次并行化在服务限制下是否仍有收益。
3. 如果岗位要求 Agent 后训练，再建设轨迹数据、动作空间、SFT/DPO 训练和独立测试集，不应仅把现有编排代码改名。

项目操作见 [新手说明与操作指南](./新手说明与操作指南.md)。
